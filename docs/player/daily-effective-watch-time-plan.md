# 当日有效播放时长缓存方案

状态：有效时长缓存、普通播放页 / For You 计时接入，以及普通播放页观看任务自动领取已实现。真机后台、锁屏、广告及真实服务端领取仍需联调验收。

## 1. 目标与统计口径

为当前用户维护全局、可持久化的当日有效播放时长，合并普通短剧播放页（singleDrama）和推荐 Tab（forYou）的观看。退出播放页、切换 Tab、切集、进程重启后，同一天继续累计。

- 按真实经过的时间计时，内部保存毫秒，对外提供向下取整的累计秒数；不能每次采样都截断小数。
- 正常播放且内容实际推进才计入。暂停、广告、打开播放源、首帧等待、缓冲、拖动与跳转等待、后台、锁屏、结束、错误、锁集等待均不计入。
- 拖动跳过的区间不计入；跳转结束后播放尚未观看的内容才恢复计时。
- 倍速只改变内容覆盖速度：2 倍速实际播放 10 秒，最多累计 10 秒；0.5 倍速实际播放 10 秒，同样最多累计 10 秒。
- 重复观看暂定义为“同一用户、同一天、同一集的同一内容区间”不重复计入。部分重复时只计新增区间对应的实际时间；不是看过一集就整集不再统计。
- 两个入口共享去重记录；推荐 Tab 看过的区间，进入短剧播放页重看不再增加。
- 按印度标准时间（IST，UTC+05:30）每天 00:00 开始新的一天，重新累计并重新建立去重区间。本方案不采用跨天终身去重。
- 暂定合法试看中实际播放的正片也计入，试看结束后的等待不计入；后续若奖励规则排除试看，通过统一资格策略调整，不沿用自动收藏的排除条件。

## 2. 当前代码与接入位置

- `lib/features/player/presentation/pages/player_page.dart` 同时承载 singleDrama 和 forYou，已有前后台、路由覆盖、推荐 Tab 可见性判断。
- `lib/features/player/application/player_playback_controller.dart` 提供真实播放状态与 positionStream 消费入口，包含首帧、缓冲、seek、结束等状态。
- `PlayerAutoFavoriteTracker` 只服务一次访问中的自动收藏，没有持久化和区间去重，不能直接作为新的全局计时器。
- 当前观看进度接口的 `watchSecond` 是媒体位置，不能当作有效观看时长。保持该接口原有语义。
- 已有 SharedPreferences 缓存模式可复用，但不能复用续播缓存的数据或淘汰规则：续播位置无法还原实际看过的区间，当日去重记录也不能因条数上限被提前删除。

## 3. 分层设计

当前实现包含以下组件：

| 层 | 组件 | 职责 |
| --- | --- | --- |
| domain | DailyEffectiveWatchSnapshot | 用户、日期、累计毫秒、各集已看区间、版本 |
| domain | EffectiveWatchAccumulator | 纯计算：样本连续性、真实时间换算、区间差集与合并 |
| domain | DailyEffectiveWatchRepository | 当日快照读写契约 |
| data | SharedPreferencesDailyEffectiveWatchRepository | 序列化、读写队列、版本与损坏处理 |
| application | DailyEffectiveWatchController | 应用级 Riverpod 单实例，账号/跨日/持久化/状态发布 |
| presentation / application | PlayerPage 门禁 + PlayerPlaybackController 原始位置回调 | 汇总可见性、播放状态和广告阻断，所有程序化 seek 打断计时，不另建桥类 |

全局 Controller 不使用按播放会话隔离的 family，也不随页面退出自动销毁。播放会话仅持有桥和 owner token。领域计算不依赖 Flutter、网络或奖励 UI，便于用可控时钟测试。

同一时刻只允许一个前台可见的播放会话拥有计时权。For You 跳入短剧页时先结算旧 owner，再授予新 owner；旧 owner 的延迟回调、释放请求不能影响新 owner。预加载会话永远没有计时权。

## 4. 有效播放门禁

统一资格条件同时满足才接收有效样本：

1. 用户身份已加载且具有稳定 userId（包含服务端分配了 ID 的游客）；无身份时不累计，也不事后归给另一个用户。
2. App 生命周期为 resumed，页面没有被其他路由遮挡；For You 还要求当前选中推荐 Tab。
3. 会话持有计时权，媒体对应当前落位的剧集，且为短剧正片。
4. 正在播放、已有解码首帧且首帧已实际渲染到 Surface，非 buffering/opening/seeking/ended/error/blocked/waitUnlock 等不可播放状态。
5. 未处于进度条拖动、程序化 seek、恢复位置或换源等待阶段。
6. 未展示/播放广告，未被锁集或付费阻断。

广告需要显式阻断信号，不能只依赖“广告一般会暂停播放器”。生命周期一旦离开 resumed 即停止；恢复前台、解锁、返回 Tab 后必须用新的媒体样本重新建立基线，不能补算离开期间的时间。

门禁关闭时，仅结算到最后一个已确认推进的媒体样本，不把尚无媒体证据的等待尾部加入统计。普通控制浮层若不遮挡正片且不暂停播放，不应单独阻止计时。

## 5. 真实时间累计与内容区间去重

### 5.1 两种时间分别使用

- 用单调时钟（Stopwatch，可注入）计算真实经过时间，避免设备时间校准改变累计值。
- 用实际媒体位置标记看过的内容，以 `(dramaId, episodeId)` 为稳定键，不使用会话 ID、URL、清晰度或列表 index。
- 用日期时钟划分任务日，不能拿日期时钟差值直接作为播放时长。

### 5.2 连续样本算法

每个样本携带 owner、账号代次、播放代次、剧集、单调时间、媒体位置、播放速率和门禁状态。只消费原始播放位置更新，不使用进度条预览或 seek 写入的 UI position。

对于同一连续播放段中的前后两个样本：

1. 计算真实时间差 `dt` 和正向媒体推进区间 `[p0, p1)`。
2. 若时间无效、位置不推进、发生回退/循环/seek、身份或播放代次变化，则不累计此跨界差值，重新建基线。位置停滞时也更新采样基线，避免后续把停滞时间补回来。
3. 校验推进量与当前速率及 `dt` 是否合理，容忍播放器位置回调的正常抖动；异常跳跃或过长的无样本间隙保守丢弃并重新建基线。当前最大样本间隙为 2500ms，媒体推进误差容差为 500ms，墙钟与单调时钟差值偏离超过 250ms 则丢弃。已覆盖对应单测，后续结合真机回调分布校准；不能把长时间无回调直接认作持续有效播放。
4. 从该区间中减去当天已观看区间，得到新增媒体长度 `unseenMs`。
5. 新增有效时间为 `dt × unseenMs / (p1 - p0)`，最大不超过 `dt`。保留计算余数，避免大量小样本产生截断损失。
6. 将本次确认播放的区间合并进已观看集合，与累计有效时间一起更新。

例如：已看 `[0, 20)`，当前连续播放 `[10, 30)`，实际用时 10 秒，新增内容占一半，累计增加 5 秒。若完全重复则增加 0 秒。

变速时结束旧采样段、在新速率下重建基线；seek 开始时断开基线，seek 完成且收到真实播放样本后重建，不跨 seek 计算区间。换源、清晰度切换、自动重播同样处理。同一连续样本内按稳定速率近似分摊真实时间，精度受位置回调频率影响，不能宣称帧级精度。

直接由实际位置流驱动累计，发布不可变快照，消费者用 select 订阅累计秒数；额外计时器仅用于落盘和跨日检查，不凭定时器 tick 增加时长。

### 5.3 去重结构

每集保存排序、互不重叠的半开毫秒区间，合并重叠或严格相邻区间，保留拖动跳过的空洞。不要只保存最远播放位置，也不要将整秒桶提前标记为全部已看，否则会漏算短片段。

## 6. 缓存与生命周期

建议每个账号、每个任务日使用独立 key：`player.daily_effective_watch.v1.<encodedUserId>.<dayKey>`，同一个 JSON 同时保存总时长与去重区间：

```json
{
  "version": 1,
  "userId": "123",
  "dayKey": "2026-09-10",
  "dayPolicy": "india-ist-v1",
  "creditedMs": 12500.5,
  "ranges": {
    "[\"10\",\"101\"]": [[0, 20000]]
  }
}
```

creditedMs 保留毫秒小数，totalEffectiveMs / totalEffectiveSeconds 对外向下取整；内容区间长度不等于实际累计时间，因此不能从 ranges 反算累计时长。

- 初始化先恢复当天快照，再按顺序处理初始化期间的有界样本队列；加载失败或队列超限保守放弃未确认样本，不覆盖有效旧快照。
- 内存实时更新，脏数据建议每 5 秒写入一次；暂停、切集、离开入口、进后台、换账号时请求立即 flush。
- 所有写入串行化，每段事件捕获用户身份，按同一队列完成加载、累计和写入，防止旧异步写入覆盖新数据；同一份快照中的总量和区间一起写入。
- 退出播放页只释放 owner，不清空当天累计；重启恢复累计和区间，但不恢复 runningSince 等运行态。
- 换账号先停止旧会话、结算并保存旧账号，再加载新账号；旧回调丢弃。退出登录后不继续计入旧账号，重新登录同账号可恢复当日记录。
- 保留当前及最近 7 个日期分区供日期回切读取，清理过期记录；不得为压缩缓存删除当天已看区间。观察区间数量与写入体积，若真实使用规模超出 SharedPreferences 适用范围，再迁移仓储实现。
- 校验版本、用户、日期、非负有限时长及区间合法性。损坏数据不凭续播位置补算；记录诊断信息并保守重建，避免影响播放。
- 写入失败不弹 Toast，保留内存脏状态并重试。异常杀进程可能丢失最后一次未落盘片段，正常情况下窗口约 5 秒；系统终止和存储失败时无法保证这个上限。

## 7. 日期切换

通过可注入的 DayPolicy 定义 dayKey 和下一个日界，固定采用印度标准时间（IST，Asia/Kolkata，UTC+05:30）每天 00:00 重置，与现有奖励、签到和任务的印度时区刷新口径一致。现有规则文案位于 `lib/l10n/app_localizations.dart`。不使用设备本地自然日，设备所在时区或时区设置变化不改变任务日。

计算时先将当前时间转换为 UTC，再加 5 小时 30 分钟，取年月日作为 dayKey；以该印度日期的次日 00:00 减去 5 小时 30 分钟得到下一个 UTC 日界。例如印度时间 2026-09-11 00:00 对应 UTC 2026-09-10 18:30、中国时间 2026-09-11 02:30。

- 在每次样本处理、读取快照、恢复前台时检查日期；前台另设日界检查，避免暂停跨夜仍暴露昨天总量。
- 连续有效播放跨印度时间午夜时，按日界将真实时间和媒体区间成比例分成两段，各自计入所属日期；昨天已看区间不带入今天。
- 印度时间午夜后台或锁屏时只换日期，不新增时长。
- 检测系统时间跳变时打断基线，重新读取目标印度日期的已有分区，不用墙钟跳变量加时，也不覆盖已存在分区；仅设备时区变化不触发重置。
- 本地缓存只覆盖当前设备，清数据、换设备、修改日期无法提供权威防重复保证。后续奖励资格、领奖幂等与跨设备一致性由服务端确认。

## 8. 奖励协调器边界（已接入）

全局层只暴露 `userId / dayKey / totalEffectiveMs / totalEffectiveSeconds / ready` 等只读状态，以及 `flush` 能力，不调用领奖接口，不展示 Toast。

独立的 PlayerWatchRewardCoordinator 监听这些状态：进入普通短剧播放页请求播放任务；达到时长且仍在前台普通播放页时调用领取接口；成功 Toast，失败或异常静默。For You 只贡献时长，不查询或领取任务；在 For You 达标后进入普通播放页，主动检查已达标任务，无需等累计秒数再次变化。

缓存层本身仍不包含接口或 UI 操作；自动收藏规则保持独立。观看任务的接口与重试规则见第 11 节。

| 场景 | 预期 |
| --- | --- |
| 1 倍速首次连续看 30 秒 | 约累计 30 秒，误差限定在采样边界 |
| 2 倍速/0.5 倍速首次实际看 10 秒 | 均约增加 10 秒 |
| 先看 10 秒，拖到 60 秒后再看 10 秒 | 共约 20 秒，跳过区间不标记 |
| 回拖到已看区间、循环重播 | 重复区间增加 0，仅新增区间计时 |
| For You 看后进入普通页重看同一片段 | 总量不因入口切换重复增加 |
| 暂停、缓冲、首帧等待、广告、后台、锁屏各 30 秒 | 各增加 0；恢复后不补算等待 |
| 切换 Tab、路由覆盖、预加载及旧会话延迟回调 | 隐藏或非 owner 会话增加 0 |
| 同日正常退出重进、重启 | 恢复总量和去重区间 |
| 账号 A/B 来回切换、加载和写入存在延迟 | 各自隔离，无串号和旧写覆盖 |
| 连续播放跨印度时间午夜、后台跨印度时间午夜 | 在 IST 00:00 正确分日，后台不计时 |
| 设备在中国或其他时区、切换设备时区 | 始终按 IST 00:00 重置，设备本地午夜不重置 |
| 时钟回拨、位置跳跃、回调停滞、损坏缓存、写入失败 | 不产生异常时长，不阻塞播放 |

重点测试采用假单调时钟、假日期时钟和真实区间输入，不用实际 sleep。

## 11. 观看任务自动领取

### 接口

- `GET /api/activity/task/list`，query 为 `businessType=2`、`rewardType=0`，同时获取金币与会员积分观看任务。
- 复用奖励模块 DTO，将 `targetValue`、`progressValue`、奖励数量等 int64 数值字符串解析为 Dart int。
- 本地当日累计有效秒数达到 `targetValue` 且 `claimed=false` 时尝试领取。后端 `completed=false` 不阻止这次尝试，以允许客户端与后台计时存在误差；不将服务端 progressValue 与本地时长相加。
- `POST /api/activity/task/reward/claim`，JSON 为 `{"taskKey":"任务配置键"}`。
- 完整保留 `CLAIM_STATUS_PENDING`、`CLAIM_STATUS_PROCESSING`、`CLAIM_STATUS_SUCCESS`、`CLAIM_STATUS_RETRY`、`CLAIM_STATUS_FAILED`；只有精确的 `CLAIM_STATUS_SUCCESS` 提示成功。

### 档位与重试

1. 金币和会员积分分别选择当前已达标的最高时长档位，互不挤占；同档位不同任务依次领取。
2. 第一次达标请求失败、异常或返回非成功状态，之后每增加 60 秒有效播放重试一次，最多额外 3 次，即每任务最多 4 次尝试。例如 300 秒任务在 300、360、420、480 秒尝试。
3. 达到同奖励类型的下一档，就停止上一档重试；下一档即使已领取或重试耗尽，也不回退补领旧档。
4. 离开普通播放页、进入后台、锁屏或广告时，不发起领取。返回后重新查询任务，结合已有累计时长继续检查；迟到/错过的多个重试时点不集中补发，相邻实际尝试之间至少新增 60 秒有效时长。
5. 查询列表失败静默，返回页面时可重新查询，或再增加 60 秒有效观看后重试查询。
6. 同一应用只运行一个领取流程；网络请求期间的新时长、账号、日期和页面事件会在返回后重新检查。离页或换账号后的旧响应不显示 Toast。

### 记录与成功处理

- `SharedPreferencesWatchRewardAttemptStore` 按用户和印度日期保存每个 taskKey 的尝试次数、最后尝试时的有效秒数、是否成功，保留最近七个日期分区。
- 请求前先保存已使用的尝试次数，避免重启或响应不确定时重新获得整轮重试机会。记录写入失败时不发出未记账请求，也不提示错误。
