## 分析播放器自动领取奖励逻辑

梳理了 `lib/features/player` 下的观看奖励链路，两层架构：

**计量层** `application/daily_effective_watch_controller.dart` + `domain/daily_effective_watch.dart`
- 播放内核 position 流 → `player_playback_controller._emitEffectiveWatchPosition` → `player_page._onEffectiveWatchPosition` → `DailyEffectiveWatchController.observe`
- `EffectiveWatchAccumulator` 做本地反作弊：单调时钟 vs 墙上时钟偏差 ≤250ms、0<elapsed≤2500ms、位置前进量与 elapsed*rate 偏差 ≤500ms
- `credit()` 按 (dramaId, episodeId) 维护已看区间，只给 unseen 部分计时（`elapsedMs * unseen / (endMs-startMs)`）
- 账本在 SharedPreferences，按 IST(UTC+5:30) 日切，与设备时区无关；5 秒定时 flush + 串行的 `_enqueue` 队列

**领取层** `application/player_watch_reward_coordinator.dart`
- `PlayerWatchRewardCoordinator`（app 级单例，provider: `player_watch_reward_coordinator_provider.dart`）
- 页面监听 (userId, dayKey, ready, totalEffectiveSeconds) 变化 → `_syncWatchRewards()` → `coordinator.update(...)`
- 流程：拉任务 `/api/activity/task/list?businessType=2` → 过滤（金币/积分 + DAILY/ONCE）→ 选当前最高档 `_isLatestTier` → 限流（已成功/≥4 次/60 秒冷却）→ 预扣 count+1 先落盘 → `POST /api/activity/task/reward/claim` → 仅 `CLAIM_STATUS_SUCCESS` 算成功
- 成功后 `onGranted` 刷新权益+余额（金币走 rewardCoinsController，积分走 memberPointsController），`onSuccess` 弹 Toast
- 领取失败完全静默，无 toast 无日志，靠 60 秒退避重试，最多 4 次网络尝试
- 只在 `PlayerFeedMode.singleDrama` 模式启用；广告解锁页/付费墙/后台/路由被覆盖时 leave + stop 不计时

## 约定/注意
- 有效时长账本纯本地，客户端可篡改，服务端 claim 侧应有校验（客户端代码看不到）
- 成功依赖服务端重新拉取的任务列表为权威，本地 `history.succeeded` 只是保险
